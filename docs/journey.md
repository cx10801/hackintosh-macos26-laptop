# 完整历程：从「能不能装」到「能日常用」

9 天，五个阶段。每个阶段记的是**当时以为的问题**和**实际的问题**——这个落差才是经验。

---

## 阶段 0 · 前置：虚拟机试水（10-18）

在动真机之前，先用 VMware 装了一遍 macOS 26。

**目的**：确认安装镜像可用、确认自己对安装流程的理解没有偏差。

**拦路的问题**：VMware 不认 `.dmg` 恢复镜像，需要先转成 `vmdk`。转完启动卡在苹果 logo。

**结果**：虚拟机最终能进系统，但显卡是软件模拟，慢到无法使用。价值在于——**把安装流程完整走了一遍**，知道每个阶段大概长什么样、大概要多久。

**这步不能省。** 真机上做第一次安装，如果连「进度条走多久算正常」都不知道，会误判很多正常现象为故障。

---

## 阶段 1 · 评估与选型（10-25 白天）

先做了硬件清查，结论很明确：

| 组件 | 判断 |
|---|---|
| CPU | Raptor Lake-HX，需 `ProvideCurrentCpuInfo`，可用 |
| 核显 | 设备 ID 不在 macOS 支持列表，**不可用** |
| 独显 | RTX 4060 Laptop，官方不支持，**只能靠第三方驱动** |
| 无线 | Intel AX201，需 `itlwm`，可用但非原生 |
| 声卡 | Conexant，需 AppleALC + 正确的 layout-id |

**关键决策：屏蔽核显，走独显直通。**

理由是核显根本驱动不起来，留着只会导致显示输出混乱。屏蔽方式是在 `DeviceProperties` 里给核显的设备路径加 `disable` 属性，或者在 BIOS 里切到独显模式。

这一步决定了整个项目的技术路线，也决定了上限——**所有显示都依赖一个非官方驱动**。

### 一个被否掉的方案

考虑过「核显输出画面 + 独显做计算」。理论上 macOS 支持这种分工（iMac 就是这么做的），但前提是核显被支持。这台机器的核显不被支持，方案不成立。

## 阶段 2 · 首次安装：三连挫（10-25 晚 → 10-26）

### 2.1 卡在安装进度条

第一次进安装器，进度条走到约 1/5 就不动了，等了 40 分钟无变化。

**当时的判断**（错的）：镜像损坏。
**实际的判断**（对的）：USB 映射没有配好。

排查方法：打开 OpenCore 的调试日志（`Misc → Debug → Target = 67`），看到安装器在挂载根分区时反复重试。原因是 USB 端口映射不正确，安装介质所在的端口被映射成了内部接口，安装器读不到。

**教训：安装阶段的卡死，90% 是 USB 或存储相关。** 先用 USB 映射工具（USBToolBox）生成正确的映射，再谈其他。

### 2.2 OpenCore 有 macOS 条目，回车进了 Windows

这个问题花了最久，因为现象极具误导性。

**症状**：OpenCore 启动菜单里能看到「macOS Installer」，选中回车，屏幕闪一下，进了 Windows。

**走过的弯路**：

| 尝试 | 结果 |
|---|---|
| 重新生成 SMBIOS | 无效 |
| 换 OpenCore 版本 | 无效 |
| 重建整个 EFI | 无效 |
| 怀疑 SSD 不兼容 | 换了个盘，仍然无效 |

**真正的根因**：UEFI 固件里的启动项顺序。这台机器的 BIOS 有一个「Windows Boot Manager」优先的强制策略，OpenCore 传递启动参数后，固件仍然按自己的顺序启动了 Windows。

**解法**：在 BIOS 里把 OpenCore 的启动项排到第一位，并删除残留的 Windows Boot Manager 条目（它会在每次启动时被重建，所以要在 Windows 里用 `bcdedit` 清理）。

**为什么难查**：日志里看起来一切正常——OpenCore 正确识别了分区，正确传递了参数，然后「正常地」启动了 Windows。实际上是固件层覆盖了 OpenCore 的决定。

### 2.3 推倒重来

10-26 上午，前面的尝试全部作废，决定重建。

```
ocboot_EFI_backup_20261026-080847    ← 备份当时的 EFI
ocboot_EFI_backup_20261026-080853    ← 五分钟后又备份一次
```

**为什么五分钟内备份两次**：第一次备份完立刻改了一个参数，改完发现不确定改对了没有，又备份了一次。事后看这个习惯救了一次——第二个备份是可启动的版本，第一个不是。

### 2.4 换用第三方 EFI 生成工具

手写 config.plist 走不通后，换了一个社区工具自动生成（本文称 1401）。它根据硬件报告生成一整套 EFI，包括 SSDT、kext、Quirks。

**第一次尝试仍然失败**：生成的 EFI 在 OpenCore 里只显示 Windows，看不到 macOS。

**原因**：工具默认按「核显输出」配置，而这台机器的核显被屏蔽了。显示通路不对，安装器起来后没有输出，看起来像「没启动」。

**解法**：开启混合输出模式（`-vi2c-force-polling`），让系统在有核显和无核显之间做兼容处理。

## 阶段 3 · 能进系统，但输入设备全废（10-26）

开启混合输出后，成功进了恢复模式。**但触控板、键盘、鼠标全部不工作。**

这是最绝望的时刻——系统进去了，但什么都点不了。

### 排查顺序

1. **USB 是否工作**：插了个 U 盘，灯亮了但系统不认 → USB 映射有问题
2. **是否 kext 没加载**：日志里看 `USBToolBox` 和 `UTBDefault`，加载了但没生效
3. **是否接口类型判断错误**：打开 USB 映射工具，发现所有端口都被标记为 `Internal`

**根因**：自动生成的 USB 映射把内置键盘（走 USB 的 HID 设备）和触控板（走 I2C）都归类成了内部接口，而 macOS 对 `Internal` 类型的端口不加载 HID 驱动。

**解法**：手动修正 USB 映射表，把键盘端口改成 `Keyboard`，触控板走 I2C 路径单独处理。

**I2C 触控板是另一个坑**：需要 `VoodooI2C` + `VoodooI2CHID`，且要配合正确的 ACPI 补丁。本机最终只做到「基础移动可用」，多点手势不完整——GPIO 中断的配置一直没调对。

## 阶段 4 · 显卡点亮，但屏幕是倒的（10-26 晚 → 10-29）

### 4.1 显卡驱动

用第三方 NVRM 驱动（2.6.5），通过启动参数传入配置：

```
nvfb=1 nvaccel=1 nvfbheads=4 -nvkmsnosmooth gfxrst=4
```

驱动加载后 Metal 可用，分辨率正确。**这是整个项目最关键的突破**——没有这个，前面所有工作都没有意义。

详见 [`nvrm.md`](nvrm.md)。

### 4.2 屏幕倒挂

机器装的是倒挂面板（或排线定义相反），Windows 下靠驱动旋转 180°。macOS 没有这个能力。

**走过的方案**：

| 方案 | 问题 |
|---|---|
| 系统设置的「旋转」 | macOS 桌面版没有这个选项（只有 iOS 有） |
| `displayplacer` 之类工具 | 只能改分辨率和排列，改不了旋转 |
| 修改 EDID | 理论上可行，但需要注入自定义 EDID，风险高 |
| **修改显示 kext** | **可行，但要重新签名** |

最终走了修改 kext 的路线：在 framebuffer 初始化时对扫描方向做翻转。这个过程需要构建一个修改过的 kext、处理签名、并在每次系统更新后重新做一遍。

**代价要说清楚**：这不是「配置一下」，是「维护一个私有内核扩展」。系统一更新，它可能就失效。

### 4.3 构建与备份

10-29 做了这个 kext 的构建和备份。备份的意义在于——**这是自己构建的、无法从任何地方重新下载的产物**。丢了就要重做一遍逆向和修改。

## 阶段 5 · 能用了，但随机崩溃（10-31）

### 5.1 症状

开机后约 35–45 秒，大约 35–45% 的概率触发内核 panic：

```
panic(cpu 0 caller ...): [kalloc.type.var6.16]: element modified after free
```

如果堆检测器没抓到，驱动会挂在 GSP 初始化上，然后被 OpenCore 的看门狗重启。

### 5.2 排查路径

| 假设 | 验证方法 | 结论 |
|---|---|---|
| 内存条故障 | 换成单条、交换插槽 | 排除 |
| SMBIOS 配置问题 | 换机型 | 排除 |
| ACPI 补丁冲突 | 逐个禁用 SSDT | 排除 |
| 启动参数不足 | 加延迟参数 | **部分有效** |
| 驱动缺陷 | 读 panic backtrace | **确认** |

### 5.3 关键发现

panic 的调用栈非常明确：

```
_nv_alloc_pages → _osAllocPagesInternal → _memdescAlloc
→ _gpuCreateRusdMemory_IMPL → _memmgrStateInitLocked_IMPL
→ _gpuStateInit_IMPL → _RmInitAdapter → NVRM::go
```

全部在 NVRM 驱动内部，发生在 GPU 状态初始化的内存分配路径上。**这是驱动的 use-after-free，不是配置问题。**

而且找到了一个具体的疏漏：驱动的安装脚本只对 Turing 架构（设备 ID `1[eEfF]??` / `21[89a-fA-F]?`）自动追加延迟参数，**Ada Lovelace（`28a0`）不在匹配范围内**，所以这台机器实际上没有应用任何缓解措施。

详见 [`panic-analysis.md`](panic-analysis.md)。

### 5.4 处置

加 `nvrmsettle=10000` 可以显著降低触发概率，但**不能根治**——它只是让竞态窗口变小，底层的 use-after-free 依然存在。

这是「缓解」不是「修复」。这个区分很重要：如果是修复，就可以宣称问题解决；是缓解，就必须在文档里写明「仍有概率崩溃」。

## 阶段 6 · 收尾（11-03）

系统稳定后，清理了安装用的辅助分区（1401 盘，5 GB FAT32）。

**清理前确认了三件事**：

1. OpenCore 的引导文件在 EFI 分区，不在这个盘上
2. 这个盘里没有自己构建的 kext（那个已单独备份）
3. 删掉后能正常启动（先改名测试，确认无影响再删）

## 如果重来一次，我会怎么做

1. **第一天就打开 OpenCore 的完整日志**。前面两天有大量时间浪费在猜。
2. **先做 USB 映射再做别的**。输入设备不通，后面所有调试都无法进行。
3. **每次改动前备份 EFI，命名带状态**（`EFI-1026-bootable` 而不是 `EFI-new`）。
4. **区分「配置错」和「驱动缺陷」要尽早**。前者能改，后者只能绕。判断错了会一直改配置，永远改不好。
5. **不要相信「自动生成」**。工具生成的 EFI 是起点，不是终点——它的默认假设（核显可用）和这台机器完全相反。
