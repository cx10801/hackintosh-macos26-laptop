# 第三方 NVIDIA 驱动

> 本文不提供驱动文件，只记录部署方式、参数含义与已知限制。

---

## 1. 背景

macOS 从 10.14 Mojave 起停止提供 NVIDIA Web Driver。此后所有 NVIDIA 显卡在 macOS 上只有两条路：

1. 用 Apple 内置的驱动（仅支持少数旧型号，且随系统版本逐步移除）
2. 用社区重新实现的驱动

本项目用的是后者。它的原理是重新实现 NVIDIA 内核扩展（`NVRM`）的接口层，把 GPU 命令翻译成 macOS 的图形栈能理解的形式。

**必须清楚的三个事实**：

- 这不是官方驱动，没有质量保证
- 它绕过了代码签名与系统完整性保护
- 每次 macOS 大版本更新都可能失效

---

## 2. 部署方式

### 2.1 前置条件

| 条件 | 说明 |
|---|---|
| SIP 部分关闭 | 需要能加载未签名 kext |
| AMFI 放行 | `amfi_get_out_of_my_way=0x1` + `AMFIPass.kext` |
| 核显屏蔽 | 否则显示通路冲突 |
| 正确的 SMBIOS | 无核显机型（见 `opencore.md`） |

### 2.2 安装流程（概念性）

```
1. 将驱动 kext 放入 /Library/Extensions 或 EFI/OC/Kexts
2. 重建内核缓存
3. 在 boot-args 中启用驱动
4. 重启
```

具体命令取决于驱动分发方式（有的提供安装脚本，有的需要手动放置）。

### 2.3 启动参数

| 参数 | 作用 | 建议值 |
|---|---|---|
| `nvfb=1` | 启用 framebuffer（显示输出） | 必开 |
| `nvaccel=1` | 启用 GPU 加速（Metal） | 必开 |
| `nvfbheads=4` | 显示头数量 | 按实际接口数，笔记本通常 4 |
| `-nvkmsnosmooth` | 关闭 KMS 平滑，减少撕裂 | 建议开 |
| `gfxrst=4` | 图形复位策略 | 4 在多数机器上稳定 |
| `nvrmsettle=10000` | GPU 初始化延迟（毫秒） | **强烈建议**，见 panic 分析 |

### 2.4 验证是否生效

```bash
# 1. 看 kext 是否加载
kextstat | grep -i nvrm

# 2. 看 GPU 是否被识别
system_profiler SPDisplaysDataType

# 3. 看 Metal 是否可用
# 打开「关于本机 → 系统报告 → 图形卡/显示器」
```

三项都正常，才算真的驱动起来了。**「能显示画面」不等于「加速可用」**——软件渲染也能出画面，但慢到不可用。

## 3. 能力边界

| 功能 | 状态 | 说明 |
|---|---|---|
| 基础显示输出 | 可用 | |
| Metal 加速 | 可用 | 但不是全部特性 |
| 多显示器 | 部分 | 取决于 `nvfbheads` 与接口映射 |
| 硬件视频编解码 | 不可用 | 需要 NVENC/NVDEC，驱动未实现 |
| CUDA | 不可用 | 无 CUDA 运行时 |
| 外接 eGPU | 未测试 | |
| 睡眠唤醒 | 不可用 | 唤醒后黑屏 |
| 亮度调节 | 部分 | 依赖具体的背光实现 |
| 外接显示器热插拔 | 不稳定 | 建议插好再开机 |

### 最影响体验的两条

**没有硬件视频编解码**：看 4K 视频、剪视频全靠 CPU，风扇会狂转。这不是配置能解决的。

**不能睡眠**：合盖会睡，但唤不醒。实际使用必须禁用睡眠，代价是电池消耗。

---

## 4. 系统更新的风险

这是整个方案最脆弱的地方。

| 更新类型 | 风险 | 应对 |
|---|---|---|
| 小版本（26.7.1 → 26.7.2） | 中等，可能失效 | 更新前备份 EFI 与 kext |
| 大版本（26 → 27） | 高，大概率失效 | 等驱动适配，不要急 |
| 安全响应更新 | 低 | 通常无影响 |

### 更新前的标准动作

```bash
# 1. 备份 EFI 分区
sudo cp -R /Volumes/EFI/EFI /Volumes/数据盘/EFI-backup-$(date +%Y%m%d)

# 2. 备份自建的 kext（无法重新下载的那些）
sudo cp -R /Library/Extensions/NVRM.kext ~/backup/

# 3. 记录当前 boot-args
nvram boot-args

# 4. 确认有可用的恢复介质
```

**第 2 步最容易被忽略。** 系统更新可能会删除或替换 `Library/Extensions` 里的内容，自己构建的 kext 丢了就要重做。

## 5. 与官方驱动的差异

| 维度 | 官方（历史版本） | 本项目所用 |
|---|---|---|
| 签名 | Apple 签名 | 未签名，需绕过 AMFI |
| 更新节奏 | 跟随系统 | 社区维护，滞后 |
| 功能完整度 | 完整 | 显示 + 计算，缺编解码 |
| 稳定性 | 生产级 | 实验级 |
| 支持范围 | 到 10.13 | 到当前系统（尽力） |

---

## 6. 判断「是不是驱动的问题」

排查时最常犯的错是把驱动缺陷当成配置错误。一个简单的判断方法：

| 现象 | 更可能是 |
|---|---|
| 完全黑屏、无输出 | 配置（framebuffer 参数、SMBIOS） |
| 能显示但分辨率不对 | 配置（EDID、display 属性） |
| 能显示但卡顿 | 配置（加速未启用）或驱动（加速不完整） |
| **随机崩溃、时序相关** | **驱动缺陷** |
| 特定操作必崩（如开某个应用） | 驱动缺陷 |
| 睡不醒 | 通常是驱动或 ACPI |

**随机性是最强的信号**：配置错误是确定性的，驱动缺陷才表现为概率。

---

## 7. 态度

这个驱动让一台「理论上不可能」的机器跑起了 macOS。从工程角度它很了不起。

但用它做生产力工具，要有清醒的预期：

- 你的系统随时可能因为一次更新而无法启动
- 你的崩溃日志不会被 Apple 受理
- 你的问题在社区里可能永远没人回答

**它是一个技术验证项目，不是一个产品。** 用它的人应该知道这个区别。
