# 倒挂屏的 180° 旋转

## 1. 现象

系统能进，显卡驱动正常，但**整个画面上下颠倒**。

这不是「屏幕装反了」那么简单——机器用的是倒挂面板，或者排线定义与常规相反。在 Windows 下厂商驱动会自动做 180° 旋转，用户感知不到。

macOS 桌面版没有这个能力。

---

## 2. 为什么系统设置里没有旋转

| 平台 | 旋转能力 |
|---|---|
| iOS / iPadOS | 原生支持，随重力感应自动切换 |
| macOS 桌面版 | **没有用户可见的旋转选项** |
| macOS（部分专业显卡驱动） | 驱动层面可以设置，但不开放给用户 |

macOS 的显示栈假定显示器是正向的。旋转在 iOS 上是常态需求，在 macOS 上是边缘需求——Apple 从未提供桌面端的旋转 UI。

---

## 3. 四种方案

### 方案 A：外部工具改显示属性

**思路**：用 `displayplacer` 或类似工具修改显示配置。

**结果**：失败。这些工具能改分辨率、刷新率、显示器排列，但旋转不在可配置项里。底层调用的私有 API 不暴露 rotation 参数。

### 方案 B：注入自定义 EDID

**思路**：EDID 里有「面板扫描方向」的位，修改后系统会按新方向初始化。

**问题**：

- 需要在 `DeviceProperties` 里注入完整的 128/256 字节 EDID
- EDID 的校验和必须重算，改错一位整个显示就废了
- 不同接口（内置屏 vs 外接）EDID 不同，要分别处理
- **最关键**：这个方案在第三方 NVIDIA 驱动下不生效，因为驱动不走标准的 EDID 解析路径

放弃。

### 方案 C：修改 framebuffer 初始化

**思路**：在驱动初始化 framebuffer 时，把扫描方向寄存器设成反向。

**可行性**：高。这是最直接的做法。

**代价**：需要修改并重新构建 kext，且每次驱动更新都要重做。

**最终选择**。

### 方案 D：硬件改造

**思路**：换排线或翻转面板物理安装。

**问题**：拆机风险、保修失效、可能损坏面板。

不考虑。

---

## 4. 方案 C 的实施

### 4.1 定位修改点

关键是找到设置扫描方向的寄存器写入位置。NVIDIA 的显示控制器有一组与「扫描方向」相关的寄存器，通常在 CRTC 初始化阶段写入。

修改思路（概念性，不含具体代码）：

```
在 CRTC 模式设置阶段，将以下标志位翻转：
  - 垂直扫描方向
  - 水平扫描方向（视面板而定，本机只需垂直翻转）
```

**注意**：如果只翻垂直，画面会上下颠倒但左右正常，这是对的。如果同时翻水平和垂直，会得到 180° 旋转——两者等价，取决于面板的实际接法。

### 4.2 构建与签名

```bash
# 1. 修改源码
# 2. 编译
xcodebuild -project NVRM.xcodeproj -configuration Release

# 3. 移除旧签名（如果有）
codesign --remove-signature NVRM.kext

# 4. 放入系统扩展目录
sudo cp -R NVRM.kext /Library/Extensions/

# 5. 重建缓存
sudo kextcache -i /

# 6. 重启
```

### 4.3 验证

```bash
# 确认加载的是修改后的版本
kextstat | grep -i nvrm

# 看加载路径与时间戳
ls -la /Library/Extensions/NVRM.kext/Contents/MacOS/
```

最直接的验证是：**画面正过来了**。

---

## 5. 备份：这一步不能省

这个 kext 是**自己构建的、无法从任何地方重新下载的产物**。

丢了意味着：重新找源码、重新定位修改点、重新编译、重新调试。

所以备份策略要和其他文件不一样：

| 备份位置 | 说明 |
|---|---|
| 数据盘 | `~/backup/NVRM-rotated-YYYYMMDD.kext` |
| 外部存储 | U 盘或移动硬盘一份 |
| EFI 分区 | 如果 kext 从 EFI 加载，EFI 备份自带 |
| 源码 | **修改后的源码单独存一份**，否则 kext 无法重新构建 |

**最后一条最重要**：只备份编译产物不够，还要备份源码改动（一个 patch 文件即可）。

```bash
# 生成 patch，便于重放
diff -u original.c modified.c > rotation.patch
```

---

## 6. 维护成本

| 场景 | 需要做什么 |
|---|---|
| 驱动更新 | 把 patch 应用到新版本源码，重新编译 |
| 系统大版本更新 | 可能需要重新定位修改点（寄存器偏移变了） |
| 换同型号机器 | 可以直接复用 |
| 换不同型号 | 修改点可能不同，要重新分析 |

**这是一项持续的维护负担，不是一次性的配置。**

如果哪天不想要了，回退方式：

```bash
sudo rm -rf /Library/Extensions/NVRM.kext
sudo kextcache -i /
# 重启
```

---

## 7. 有没有更简单的路

有，但都有明显缺陷：

| 替代方案 | 为什么没选 |
|---|---|
| 外接显示器 | 笔记本的卖点就是便携，外接违背初衷 |
| 用「镜像 + 翻转」的中间层 | 需要编写额外的图形拦截层，复杂度更高 |
| 只在需要时用虚拟机 | 性能损失太大，等于放弃这个项目 |
| 接受倒挂，练就倒着看屏幕的能力 | — |

**没有优雅的解法。** 要么改驱动，要么放弃。

---

## 8. 这件事说明了什么

黑苹果的很多「功能缺失」不是配置问题，是**架构性缺失**：macOS 的显示栈里根本没有「旋转」这个概念，所以不存在「打开某个开关」的解法。

遇到这类问题时，花在「找配置项」上的时间是浪费的。正确的判断是：**先确认这个能力在系统里是否存在**，不存在就只能改代码。

这个判断能力的价值，远大于记住任何一个具体配置。
